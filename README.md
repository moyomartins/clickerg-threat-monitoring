# ClickerG , Threat Monitoring

Click-fraud protection for PPC advertisers. Blocking is invisible by nature: the advertiser
just sees traffic disappear. This screen is the part that earns the trust , open any blocked
visitor and the whole journey is there, in language an advertiser can act on.

## Run it

```bash
npm install
npm run dev            # app          → http://localhost:5173
npm run storybook      # component library → http://localhost:6006
```

Builds and checks:

```bash
npm run build            # app → dist/
npm run build-storybook  # static Storybook → storybook-static/
npm run typecheck        # tsc -b across app + packages/ui + .storybook
npm run lint             # oxlint
npm test                 # unit tests + every story, with a11y checks
```

`npm test` runs two Vitest projects: `unit` (the scoring model and the mock-data invariants,
in Node) and `storybook` (every story rendered in headless Chromium, with interaction plays
and axe accessibility checks). Accessibility violations **fail the build** , `a11y: { test: 'error' }`
in `.storybook/preview.tsx`.

## Layout

```
packages/ui/            @clickerg/ui , the design system, an npm workspace
  src/tokens.css        every colour, type step, space, radius and shadow
  src/styles.css        component styles, built only from those tokens
  src/*.tsx             Button, StatusPill, SignalChip, Card, DataTable,
                        VisitEntry/Journey, FilterBar + fields, EmptyState,
                        Skeleton, ConfidenceMeter
  src/*.stories.tsx     stories, living next to the component they document
src/                    the Threat Monitoring app
  data/scoring.ts       the blocking model , and the source of its own explanations
  data/mock.ts          deterministic mock traffic
  VisitorList.tsx       list view: filters, sort, search, empty + loading states
  VisitorDetail.tsx     drill-down: the full journey and the verdict
.storybook/             points at packages/ui , there is no second copy of anything
```

The app and Storybook import the **same files**. `src/VisitorList.tsx` starts with
`import { Button, DataTable, … } from '@clickerg/ui'`, resolved through an npm workspace
(`node_modules/@clickerg/ui` is a symlink to `packages/ui`). Change `Button.tsx` and both
the product and its documentation change together. Nothing in `src/` hardcodes a hex value
or a magic pixel: every value resolves to a token in `packages/ui/src/tokens.css`.

## The mock data

53 visitors, generated from a fixed seed so the same journeys appear on every reload ,
a fraud screen that reshuffles between refreshes cannot be reviewed or demoed. Journeys
run from a single visit to 29, and mix paid, organic, direct and referral traffic inside
the same visitor where it makes sense. Roughly 13 blocked, 10 under review, 28 not blocked,
plus the two pinned cases below.

The three cases worth opening first (also exported as `NOTABLE` in `src/data/mock.ts`):

| IP | What it is |
|---|---|
| `41.203.88.7` | **The obvious one.** 29 paid clicks in two days from a datacenter IP, zero scroll and zero mouse movement on every one, undeliverable emails on a third of them, bot probability climbing past 95%. Blocked at paid click 3 , the timeline marks exactly where. |
| `82.14.90.221` | **The judgement call.** Reads the pages properly, converts for £249 , and clicks on a fixed 3-second cadence from a datacenter IP with 94% session-to-session similarity. We do not block it, and the detail view says plainly that this one is a tie we are handing to the advertiser. |
| `178.62.40.9` | **The edge case.** Our tag stopped reporting mid-journey. Missing signals are shown as *not captured* and excluded from scoring rather than quietly counted as clean. |

Other states worth a look: `?fail=1` forces the load error, filtering to an impossible
combination gives the "no visitors match" empty state, and the first 700ms of any load is
the skeleton.

## How the blocking decision works

`src/data/scoring.ts` holds the whole model, and it produces both the number and the
sentence , the explanation cannot drift from the maths because it is generated by the same
rules.

Each visit's signals produce a raw delta. That delta is squashed through a logistic curve
into a 0–100 risk for the visit, so one spectacular visit cannot pin the score at 100 and a
long run of mildly odd visits cannot creep there either. The journey score is an exponential
moving average of those per-visit risks , that is what makes blocking *cumulative* , plus a
small volume term, because repetition is itself evidence once the pattern already looks bad.
Non-paid visits are weighted at half: they tell us about the visitor without costing the
advertiser anything.

- **Block** at 80, and never before 3 paid clicks, however bad a single visit looks.
- **Under review** from 50.
- **Judgement call** when a visitor is both suspicious *and* has converted. Real money on one
  side, automation signals on the other , we hold rather than block a possible customer, and
  we say so rather than manufacturing confidence.

## Signals

The baseline set (IP, location, interaction level, bot probability, VPN/proxy, form-fill
deliverability, conversion) plus five invented ones, chosen because each is explainable to a
non-technical advertiser in one sentence, and all five are actually used in the reasoning:

- **Click cadence** , time between repeat clicks. Under a second is faster than the page renders.
- **Device fingerprint reuse** , the same browser appearing across sessions presenting as different visitors.
- **Session similarity** , how exactly a session repeats the previous one. People vary; scripts do not.
- **Time-of-day clustering** , visits landing inside the same narrow overnight window.
- **UTM consistency** , tracking parameters that do not match the referrer they claim.

Campaign, keyword and click cost ride along as context on every paid visit, so the advertiser
can see which campaign is paying for the traffic.

## Product decisions

- **Hash routing, no router dependency.** Two screens and one level of depth. `#/visitor/<ip>`
  gives real back/forward behaviour and shareable links in about ten lines.
- **Manual overrides sit on top of the model.** Blocking or clearing a visitor by hand changes
  the status and says so in the verdict, but never rewrites what we actually saw , the journey
  below stays intact.
- **Severity colour is an addition to the palette.** The base palette is warm-neutral by
  design, which a threat product cannot quite live inside. Three desaturated earth tones carry
  severity, always paired with a dot or a label so the UI still parses in greyscale.
- **Two accessibility deviations from the spec, both deliberate and commented in the source.**
  The pill button's 0.5 default opacity renders label text at 3.2:1 against cream, so it is held
  at 0.75; and the medium-severity tone was darkened from `#8a6b1f`, which only reached 4.01:1
  on its own tint. Both were caught by the a11y checks in `npm test`, not by eye.
- **Camera Plain Variable is not redistributable**, so the stack falls back to the humanist
  system sans the spec names (`ui-sans-serif, system-ui`). Drop the real face into the
  `--cg-font-sans` token and every screen picks it up.
